# 開発レトロスペクティブ（Phase 5時点）

# 超失敗したこと
- 責任ドリブンだとダメ。本当にゴミが出来た。
- ユーザー体験ドリブンで作るべき
- セキュリティとか保守性・運用については後でAIのフルパワーでどうにかすべき

## 目的
- 今回の開発で顕在化した課題を記録し、同じ失敗を繰り返さないための運用ルールを固定する

## 発生した課題
- 局所タスクの完了を優先しすぎて、網羅ゴールへの接続が弱くなった
- ユーザーが意思決定中の段階で、未合意の変更を先に進めてしまった
- `plan.md` のタスク完了判定と実装実態の同期漏れが発生した
- 「代表ケース1本」の達成を過大評価し、エンドポイント単位の網羅を後回しにした
- バックエンド先行で進めた結果、`inventory` / `amount` のような仕様前提の未確定事項を暫定のまま実装してしまった
- AI生成コードに対する責任を機械的に追跡するメトリクスが未整備で、評価が定性的になった

## 根本原因
- 上位ゴール（全エンドポイント網羅）より、下位タスクの形式的達成を優先した
- 着手前の拘束条件（後続網羅タスクの存在確認）を運用として徹底できていなかった
- 完了報告時に「未対応の残件」を明示しても、次タスクへの接続を固定化できていなかった
- UI操作から見た業務フローの検証が後ろ倒しになり、仕様の不自然さを早期検出できなかった

## 再発防止ルール
- 実装着手前に「今回の結果定義（達成/未達）」を明示する
- 局所固定タスクは、対象APIの網羅後続タスクが `docs/plan.md` に未完了で存在しない限り着手しない
- フェーズ完了判定は網羅マトリクス基準で行う（未対応行が1つでもあれば未完了）
- `400` は対象エンドポイントごとに入力無効組み合わせを全列挙する（`2^n - 1`）
- 指示されていない変更（方針未合意の実装・ドキュメント更新・テスト実行）は行わない
- 作業後は `plan.md` と実装差分の同期を必須チェックにする
- 仕様前提が多い領域（在庫・決済）は、フロントエンド先行またはフロント/バックエンド並行で画面操作ベースの検証を先に行う
- バックエンド実装着手条件として「UI操作で主要ユースケースが不自然なく成立すること」を確認する

## Phase 5での運用チェックリスト
- [ ] 網羅マトリクス行とテスト関数の1対1対応が維持されている
- [ ] 未対応ケースが `docs/testing-roles.md` に可視化されている
- [ ] `plan.md` のチェック状態が実装実態と一致している
- [ ] 合意前の変更を先行していない

## 追記メモ（次回改善の論点）
- 現在のように細粒度タスクを1つずつレビューするスタイルでは、1タスク単位の妥当性確認はできても、全体整合や抜け漏れ検出の確度が下がる
- 最終責任は人間が負うため、人間が把握しやすい「意味・目的の単位」でタスクを編成する必要がある
- 運用候補:
  - タスクを中間粒度（Phaseより小さく、現行タスクより大きい単位）で束ねる
  - その中間粒度単位で PR またはコミットを作る
- 現状の課題:
  - Phase単位は大きすぎる
  - 現行の1タスク単位は小さすぎる
  - 意味・目的単位でのタスク編成が不足している
- 次回開発開始前に、中間粒度の定義と運用（PR単位/コミット単位）を決める
- 次回は「FEモック実装 → 人間操作で仕様確認 → OpenAPI/plan確定 → BE実装」の順を標準フロー候補として検証する
- 次回開発開始前に、AI責任追跡メトリクス（トレース率/固定化ゲート通過率/流出率/再実行率）の定義と収集方法を決める

## AI再発防止ルールに関する注意
- AIが提示する再発防止ルールは、そのまま信用しない
- ルールが実際に再発防止できるかは検証が必要
- 再発防止策は必ず再議論し、運用可能な形に詰めてから採用する
