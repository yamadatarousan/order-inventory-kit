# 抽象から具体への写像ルール

## 目的
- `docs/context.md` の原則を、実装タスク・テスト・CIに一貫して落とし込む
- 「何を守るか（抽象）」と「どこで守るか（具体）」の対応を固定する
- レビュー時に迷わない最小判定基準（DoD）を定義する

## スコープ
- 対象: バックエンド中心のレール（契約/不変条件/構造/境界観測一貫性）
- 非対象: UI詳細設計、命名の好み、実装スタイルの微調整

## 基本原則
- 抽象だけで完了判定しない。必ず「成果物」と「CI検証」に変換する
- 変更は「どの固定条件を増やしたか」で説明する
- テストの種類ではなく「固定したい性質」で層を選ぶ

## 抽象→具体マップ
| 抽象（context） | 具体化する成果物 | 最低限の検証 |
| --- | --- | --- |
| 境界を単一参照点で固定する | `contracts/openapi.yaml` | OpenAPI差分チェックがCIで通る |
| 破壊的変更は移行に従属 | `contracts/migrations/*.yaml` | 破壊差分時に移行定義が必須になる |
| 生成整合を保つ | 生成コード（Go/TS） | 再生成後に差分ゼロ |
| 構造違反を固定化前に落とす | lint/depguard/eslint設定 | 依存方向/越境違反でCI失敗 |
| 不変条件を固定する | `backend/tests/domain/` | 性質違反ケースが失敗する |
| 境界観測一貫性を固定する | `backend/tests/boundary/` | 代表シナリオを通しで検証する |

## 実装時の落とし込み手順（最小）
1. 変更対象タスクに対して、固定する条件を1-3個に絞る
2. 各条件を「成果物」に落とす（仕様/テスト/設定）
3. 各成果物に対応するCI検証を確認する
4. 変更後に「追加した固定条件」「未固定の条件」を明示する

## DoD（完了判定）の書き方
- 良い例
  - 「`POST /orders` の200後に `GET /orders/{id}` で `confirmed` を観測するテストを追加し、CIで実行」
  - 「`InventoryRepository` の失敗時不変（在庫が変化しない）を契約テストで固定」
- 悪い例
  - 「境界テストを追加した」
  - 「互換性を担保した」

## 代表的な不足パターンと補正
- 症状: テストはあるが何を固定したか不明
  - 補正: テスト冒頭に「固定対象・対象範囲・根拠」を3-4行で記載
- 症状: `boundary` という名前だがstubのみで統合未検証
  - 補正: 「単体境界」と「統合境界」を分離し、後者は実Router+実UseCase+実DBで固定
- 症状: 破壊変更の議論がレビューで属人化
  - 補正: 差分検出と移行定義必須をCIに従属させる

## この文書の位置づけ
- 原則（Why）: `docs/context.md`
- 仕様（What）: `docs/spec.md`
- 計画（When）: `docs/plan.md`
- テスト責務（How-Test）: `docs/testing-roles.md`
- 本書（How-Bridge）: 抽象を具体へ変換する手順と判定基準
